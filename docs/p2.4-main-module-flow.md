# P2.4：主模块、功能模块与主流程

> 状态：已完成<br>
> 版本：ArchMap 1.6.0 / bundle schema 3.6<br>
> 日期：2026-11-18

## 1. 目标

P2.4 修正模块语义并把程序主流程提升为主模块的一等视图：

- 每个项目恰好一个主模块，功能模块数量可以为 0..N。
- 所有模块不再拥有僵硬的输入/输出端口节点。
- 主模块展示函数级主流程 DAG。
- 功能模块只提供 Provider、Capability 和公开接口。
- 主流程分析使用独立的 `flowRole`，不修改功能模块的 Provider Role、visibility 或 API 分类。

## 2. 模块语义

```text
主模块      项目唯一组合根，承载入口与顶层编排
功能模块    向主模块或系统其他位置暴露能力
```

模块不再表达为处理阶段，因此：

- `moduleGraphs[]` 不再包含 `inputs` / `outputs`。
- `projectGraph` 不再包含 `boundaryNodes`。
- 不存在 `module_input` / `module_output` / `project_input` / `project_output` 边。
- 项目外部输入输出留给 P4 user surface。

主模块解析顺序：

1. 显式配置 `mainModule`。
2. 拥有主 entrypoint 的模块。
3. 兼容字段 `role=main`。
4. 第一个模块作为 fallback，并产生诊断。

## 3. 主流程边界语义

主流程是**主模块的组合视图**，不是全量可达调用图。

固定规则：

1. 从 entrypoint 开始。
2. 只在主模块内部继续展开函数调用。
3. 主模块函数之间可以继续遍历；经过隐藏 helper 时使用 `call_path` + `viaFunctionIds`。
4. 进入功能模块的 canonical interface/provider 后立即停止。
5. 功能模块内部 utility、私有 helper、adapter 细节不进入主流程节点。
6. 功能模块节点必须来自 canonical `apiProviders` / `providedApis`；utility/config/model 不能成为 interface。
7. 功能模块边界节点必须 `flowBoundary=true`、`expandable=false`，且没有出边。

因此：

```text
主流程          ValidationManager.validate()
Method Detail   ValidationManager.validate() -> validate_bundle() -> ...
Trace / Impact  在 P4 中才继续穿透功能模块内部
```

这一边界保证主流程与功能模块能力页语义一致，也避免 `validate_bundle()`、`decode_message()` 等内部实现泄漏为公开接口。

## 4. 主流程数据契约

主流程位于：

```json
{
  "projectGraph": {
    "mainModuleId": "main-pipeline",
    "primaryFlowId": "main-flow:1:...",
    "mainFlows": []
  }
}
```

每个 entrypoint 生成一个 `archmap.main-flow` 对象。

### 3.1 节点

```text
entry         程序入口
orchestrator  主模块内参与编排的函数或 manager 方法
provider      被构造、上下文管理或协议消费的类 Provider
interface     功能模块公开方法/自由函数能力
dispatch      动态分发边界
```

主模块中的编排函数通过 `flowRole` 进入主流程，不要求它们是功能模块公开 API。因此主模块自由函数和内部命令处理函数可以成为流程节点，而功能模块的 Provider Role 保持不变。

### 3.2 边

```text
call          静态真实调用，实线，high
call_path      经过隐藏内部函数的压缩路径，实线，保留 viaFunctionIds
composition   动态分发/组合推断，虚线，必须 low
```

composition 永不伪装成 call。普通条件分支共享 `branchGroup`，条件文本为 best-effort元数据；循环不展开，递归回边折叠。

## 5. Dispatch 契约

动态分发使用独立节点：

```json
{
  "kind": "dispatch",
  "expression": "args.func",
  "candidateCount": 5,
  "candidateSetComplete": true,
  "candidateSource": "config",
  "unresolvedReason": null
}
```

候选来源优先级：

```text
mainFlow.dispatches 配置
  > 源码内机器可读注释
  > argparse set_defaults / 静态注册表
  > P3 类型/多态候选
  > unresolved
```

配置示例：

```json
{
  "mainFlow": {
    "dispatches": [
      {
        "function": "archmap.entry.cli_entry:main",
        "expression": "args.func",
        "occurrence": 1,
        "candidates": [
          "archmap.utility.cli_utility:cmd_build",
          "archmap.utility.cli_utility:cmd_check"
        ],
        "complete": true,
        "reason": "argparse_dispatch"
      }
    ]
  }
}
```

源码局部声明格式：

```python
# archmap:dispatch complete=true candidates=cmd_build,cmd_check
args.func(args)
```

规则：

- 只有显式 `complete=true` 才标记候选集合完整。
- 自动静态发现默认 `candidateSetComplete=false`。
- 无候选时只生成 unresolved dispatch 节点，不猜测全部主模块函数。
- 候选边是 canonical 图边：`dispatch --composition(low)--> candidate`。
- 候选很多时由 UI 折叠展示，数据层仍保留全部已知候选。

## 6. 前端

- 项目页：主模块和功能模块能力卡片。
- 主模块页：默认渲染主流程；同时提供“能力视图”切换，单模块项目仍可访问类/Provider。
- 功能模块页：Provider、提供接口、类/自由函数和内部调用，无 I/O 端口。
- 主流程节点颜色按所属模块；节点形状区分 entry/orchestrator/provider/interface/dispatch。
- composition 边使用虚线和 low 标记。
- 点击流程节点进入 Method Detail；模块徽标进入模块页。

## 7. 与 P3/P4 的关系

- P3 可增强 `provider`/`interface` 节点的继承 API、实现来源和多态候选。
- P4 可在同一主流程上叠加 impact、trace 和 user surface。
- 主流程是 CallSite 与 Capability 的只读投影，不反向修改事实层。
