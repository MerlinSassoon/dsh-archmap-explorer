# P5.1 执行流汇入与边束设计

> 状态：第一层已实现；第二、三层作为未来拓展方向保留，尚未进入实现。
>
> 适用范围：P5 有界执行流的节点、边、布局和渲染。本文不改变 P5 的入口控制骨架边界。

## 1. 核心结论

执行流中的“汇合”需要拆成三个不同概念：

1. **控制流重新汇合**：多条路径到达同一个真实后继节点。这是图本身的能力，不需要合成节点。
2. **视觉扇入/边束**：当同一个目标端口的入边过多时，为了可读性把边分组绘制。它只是渲染和布局能力。
3. **模块级边束**：同一功能模块的多条路径先形成子束，不同模块的子束再共同进入同一个目标端口。它仍然是视觉分组，不是新的执行语义节点。

因此：

> 去掉语义上的 `merge` 节点；允许多条边直接进入同一个真实节点或 `exit`。  
> 未来的“汇合”只能作为视觉边束存在，不能重新生成带语义 id 的执行节点。

## 2. 改造前的问题

P5.1 之前会为下列情况生成 `kind=merge` 节点：

- `if` 分支结束后重新汇合；
- `match` / 多分支结束后重新汇合；
- 循环完成后生成“循环完成”节点；
- 空循环体生成“空循环体”占位；
- `break` 路径汇聚到循环后的节点。

这些节点不是源码中的真实执行步骤。它们会带来以下问题：

- 用户容易把“汇合”误解为真实动作；
- 执行流节点数虚增；
- 同一节点承担分支汇合、循环退出、空体占位等多种语义；
- 布局、验证、统计和测试都要为合成节点维护额外不变量；
- 条件/case 标签被迫移到边或汇合节点附近，语义层级不够直接。

## 3. 第一层：去掉语义 merge，直接 fan-in（已实现）

### 3.1 规则

- 不再生成 `kind=merge` 执行节点。
- 多个分支可以拥有指向同一个目标节点的入边。
- 目标节点可以同时是普通后继、循环后继或 `exit`。
- 每条入边保留原始 `kind`、`label`、`confidence` 和 `evidence`。
- 不允许因为多条边进入同一节点而丢弃分支标签。
- 已经终止的分支（`return` / `break` / `continue`）不得再连接到后继节点。

### 3.2 典型变换

分支汇合：

```text
before:
branch --true-->  merge  --> next
branch --false--> merge

after:
branch --true-->  next
branch --false--> next
```

分支终止：

```text
before:
branch --true-->  return
branch --false--> merge --> next

after:
branch --true-->  return
branch --false--> next
```

循环完成：

```text
before:
loop --loop_complete--> merge("循环完成") --> next
break --break--------> merge

after:
loop --loop_complete--> next
break --break--------> next
```

没有后继节点时：

```text
loop --loop_complete--> exit
break --break--------> exit
```

### 3.3 需要处理的边界

- `if` / `match` 两条路径都连接到同一后继时，保留两条不同 kind 的平行边。
- `match` 没有 default 时，显式生成 fall-through 边到后继或 `exit`。
- `break` 没有后续节点时直接进入 `exit`。
- 空循环体没有真实 body 节点时，不生成合成“空循环体”节点；`loop_body` 可以没有目标边。
- `continue` 不生成回边，也不生成合成汇合节点。
- `return` 是 terminal sink，不指向 `exit`；只有真实到达的隐式结束路径才创建并连接 `exit`。
- 如果目标节点不存在，所有继续执行的路径统一落到 `exit`。
- 如果 `branch` / 内层 `loop` 位于循环体末尾且没有可见后继，它的未连接端口表示“隐式进入下一轮迭代”；P5 不为此生成 merge 或 back lane。

### 3.4 数据与布局影响

- 封闭节点集合中移除 `merge`。
- 执行流统计中的节点数会减少，边数可能保持不变或根据路径调整。
- `layout.ranks` 需要支持同一节点多个前驱；多入边按 lane 分配，避免标签重叠。
- validator 不再要求 `merge` 节点存在，也不允许重新出现 `kind=merge`。
- 测试需要覆盖：分支 fan-in、终止分支、循环完成、break、match 无 default、无后继落 exit。

## 4. 第二层：视觉扇入与边束（未来）

> 本层尚未实现，仅作为可读性优化方向。

### 4.1 定义

当多个边进入同一个目标端口时，可以在目标端口附近绘制视觉汇集结构，例如：

```text
edge A ─┐
edge B ─┼──▶ target port
edge C ─┘
```

该汇集结构不是节点，没有执行节点 id，不进入 `executionFlows.nodes`。

### 4.2 触发条件

建议仅在可读性确有收益时启用：

- 同一 `targetNodeId + targetPort` 有至少 2 条入边；
- 或边的路径存在明显交叉、标签重叠；
- 单条边永远不聚合。

### 4.3 保留语义

- 保留所有原始边及其 kind、label、evidence。
- 悬停或选中边束时高亮全部成员边。
- 边束可以显示成员数量，但不能替代成员的完整 source/target 信息。
- 点击边束时不能进入不存在的“汇合节点详情”；只能展示成员边或高亮路径。
- 若成员边的标签不同，标签仍需可区分，不能只保留一条摘要。

### 4.4 建议的实现边界

- 边束信息属于布局/渲染派生数据，不属于执行流语义。
- 可以由前端根据同目标端口的边自动推导，不必写入默认 bundle。
- 如果需要在布局阶段预先计算，可使用独立字段，例如：

```json
{
  "targetNodeId": "exec:...:next",
  "targetPort": "in",
  "groups": [
    {
      "key": "module-a",
      "fromModuleId": "module-a",
      "edgeIds": ["edge-1", "edge-2", "edge-3"],
      "count": 3
    }
  ]
}
```

该结构仅为候选思路，当前不进入 schema。

## 5. 第三层：模块级边束（未来）

> 本层尚未实现，适用于跨模块或混合模块表达，不建议默认进入 P5 主流程。

### 5.1 定义

同一来源模块的多条边进入同一个目标端口时，可以先按模块形成子束：

```text
模块 A 的边 A1 ─┐
模块 A 的边 A2 ─┼─ A bundle ─┐
模块 A 的边 A3 ─┘            │
                             ├──▶ 同一个目标端口
模块 B 的边 B1 ─┐            │
模块 B 的边 B2 ─┼─ B bundle ─┘
```

### 5.2 约束

- “A bundle”和“B bundle”都是视觉边束，不是节点。
- 分组键至少包含：`fromModuleId + targetNodeId + targetPort`。
- 最终目标端口仍然是同一个真实端口。
- 每个模块子束保留自己的成员边数量和来源证据。
- 悬停某个子束只高亮该模块的成员边；悬停目标端口则高亮所有模块的入边。
- 只有单条边的模块不做子束。
- 不允许跨目标端口聚合，也不允许把不同条件标签折叠成不可恢复的单一标签。

### 5.3 适用场景

- 跨模块调用总览；
- 未来扩展到多模块执行流时；
- 项目关系视图中的多模块指向同一 Provider/能力端口。

当前 P5 只展开主模块 entrypoint，功能模块接口是原子边界，因此 P5 默认执行流通常不会出现“两个功能模块各有多条边进入同一端口”的场景。本层更适合作为其他图视图的通用能力，而不是 P5 默认布局的必要条件。

## 6. 非目标

以下内容不属于本设计：

- 不恢复语句级 FunctionFlow；
- 不新增图内下钻；
- 不为异常控制、逐语句动作或数据流建模；
- 不把视觉边束伪装成语义节点；
- 不改变“进入功能模块 canonical interface 后停止”的 P5 边界。

## 7. 推进顺序与变更门槛

1. 第一层已完成：移除 `merge` 节点，实现直接 fan-in，并更新 schema、validator、布局、渲染和测试。
2. 观察真实项目中的连线密度和标签重叠。
3. 只有第一层仍不足时，才评估第二层视觉扇入。
4. 第三层只在出现明确跨模块多边同端口需求时启动，并单独更新设计文档。
5. 任何边束能力都必须坚持：视觉对象无节点 id、原始边不丢失、hover 可追溯、schema 语义不被污染。
