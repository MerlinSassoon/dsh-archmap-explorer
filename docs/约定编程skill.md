# 约定编程 Skill

> 版本：2.0（项目无关版）<br>
> 最后更新：2026-11-18<br>
> 适用范围：Python 为主，架构原则可移植到其他语言。<br>
> 目标：为任意软件项目提供一套可复用的架构、契约、编码、测试和文档约束。

## 1. Skill 定位

本 Skill 是一套**项目无关**的编程约束，不依赖任何特定项目的产品形态、内部模块名、数据格式或命令。

它的作用是：

1. 约束代码架构和依赖方向。
2. 约束接口、数据模型和副作用边界。
3. 强制为模块、类、函数、方法和测试编写功能备注。
4. 统一开发、测试、文档和提交前检查流程。
5. 让代码更容易阅读、审查、迁移和长期维护。

### 1.1 规则优先级

项目实际执行时按以下优先级处理：

```text
项目明确写出的领域规则和合规要求
  > 项目当前的数据契约/接口契约
  > 本 Skill 的通用约定
  > 个人编码偏好
```

本 Skill 不替代项目自己的产品文档、领域模型、安全规范或发布流程。项目特有规则应写入项目自己的约定文档，而不是写进本 Skill。

### 1.2 项目适配原则

项目可以将本 Skill 作为基线，并补充自己的：

- 架构分层名称；
- 依赖方向；
- 公共 API 范围；
- 数据格式和版本策略；
- 测试、构建和发布命令；
- 日志、监控、安全和合规要求。

项目补充规则应保持显式，不通过口口相传或隐含约定存在。

## 2. 核心原则

### 2.1 单一事实来源

同一项业务事实、配置、规则或状态只应有一个权威来源。

禁止：

- 同一规则在多个模块重复实现；
- 展示层重新推导业务事实；
- 文档和代码各自维护一套不同版本；
- 用缓存或派生数据反向覆盖原始数据。

### 2.2 关注点分离

代码至少应区分以下职责：

```text
入口/接口层       接收外部请求、解析输入、返回结果
应用/编排层       组织用例、事务和跨模块协作
领域/模型层       业务规则、值对象、实体和领域服务
基础设施层        数据库、文件、网络、消息队列、第三方 SDK
配置层            常量、默认值、环境参数和策略表
共享工具层        无状态、无领域含义的通用辅助逻辑
```

跨层调用必须显式，禁止通过隐藏全局状态或隐式副作用连接不同层。

### 2.3 显式契约

模块之间通过明确的接口、类型和数据结构协作。

- 公共 API 必须有稳定名称、类型签名和文档。
- 内部实现不能泄漏到公共接口。
- 数据结构变化必须有迁移路径。
- 不确定的行为必须有明确的错误处理或降级策略。

### 2.4 可验证性

每个重要行为都应有可重复验证方式：

- 单元测试；
- 集成测试；
- fixture 或样例；
- 静态检查；
- 手工验收步骤（仅限无法自动化的部分）。

### 2.5 可读性优先于技巧性

优先选择清晰、直接、容易审查的代码。

禁止为了减少几行代码而牺牲：

- 类型安全；
- 错误处理；
- 可测试性；
- 功能备注；
- 日志和可观测性。

## 3. 编码前的判断

在写代码之前，先回答以下问题：

1. **这段代码属于哪一层？**
   - 入口/接口；
   - 应用/编排；
   - 领域/模型；
   - 基础设施；
   - 配置；
   - 共享工具。

2. **它对外提供什么契约？**
   - 函数/方法签名；
   - 输入输出模型；
   - 异常和错误码；
   - 状态变化；
   - 持久化格式；
   - 网络协议。

3. **它是否持有状态或资源？**
   - 生命周期由谁管理；
   - 是否需要关闭；
   - 是否线程安全；
   - 是否可重入；
   - 是否允许并发访问。

4. **它有哪些副作用？**
   - 写文件；
   - 访问数据库；
   - 发起网络请求；
   - 修改全局状态；
   - 发消息；
   - 打印日志或用户输出。

5. **它是否改变数据契约？**
   - 如果改变，先更新契约文档和 schema/类型定义；
   - 再更新实现、校验、测试和文档。

6. **它的功能备注怎么写？**
   - 只要新增或修改了模块、类、函数、方法、测试或入口，就必须写。

## 4. 架构与依赖约定

### 4.1 推荐分层

```text
entry / interface
        ↓
application / service
        ↓
domain / model
        ↑
infrastructure / adapter
```

共享工具和配置可以被上层依赖，但不得反向依赖上层业务代码。

### 4.2 依赖方向

推荐规则：

- 入口层只负责输入解析、校验和结果输出，不承载深层业务规则。
- 应用层组织用例和事务，不直接实现基础设施细节。
- 领域层表达业务规则和数据结构，不依赖框架、数据库或网络 SDK。
- 基础设施层实现外部系统适配，通过接口被应用层调用。
- 配置层提供静态参数，不依赖业务实现。
- 工具层保持无状态、无领域含义，不依赖业务层。

禁止：

- 领域模型依赖数据库客户端；
- 工具函数依赖业务服务；
- 展示层直接拼接数据库查询；
- 适配器层反向调用入口层；
- 通过循环依赖解决模块划分问题。

### 4.3 模块边界

模块划分应依据：

- 独立的业务能力；
- 独立的状态或生命周期；
- 独立的变更原因；
- 独立的测试边界；
- 可独立描述的对外契约。

不要仅按文件数量或技术类型拆模块，也不要把所有逻辑塞进一个“万能模块”。

### 4.4 公共接口与内部实现

- 公共接口应少而稳定。
- 内部实现可以调整，但不能破坏公共契约。
- 内部工具默认不对外暴露。
- 公共接口发生变化时，必须同步更新文档、测试和调用方。

## 5. 数据契约与接口

### 5.1 数据结构

- 优先使用明确的数据结构，而不是无约束的字典。
- 公共数据结构应有字段说明、类型和默认值。
- 数据模型不得承担不属于它的业务编排。
- 序列化和反序列化逻辑应与领域规则分离。

### 5.2 输入校验

所有外部输入都必须在边界处校验：

- 类型；
- 范围；
- 必填项；
- 格式；
- 权限；
- 资源限制。

内部函数可以信任已校验的输入，但应在功能备注中说明前置条件。

### 5.3 版本与兼容性

一旦数据格式或接口被外部依赖，就必须考虑版本策略：

- 新增字段是否可选；
- 删除字段是否破坏兼容；
- 默认值如何处理；
- 旧数据如何迁移；
- 版本号在哪里声明；
- 回滚是否安全。

### 5.4 错误契约

公共接口必须明确：

- 成功返回什么；
- 可预期错误如何表达；
- 不可恢复错误如何传播；
- 是否抛出异常；
- 是否返回错误对象；
- 错误信息是否包含上下文；
- 是否允许重试。

禁止用空值、静默失败或模糊字符串代替明确的错误契约。

## 6. 状态、资源与副作用

- 有状态对象必须明确生命周期和所有者。
- 持有文件、连接、锁、线程、进程或事务的对象必须提供释放路径。
- 构造函数不应执行不可撤销的外部副作用。
- 公共函数应尽量保持幂等，除非备注中明确说明不幂等。
- 修改共享状态时必须说明并发安全策略。
- 日志、监控和审计不能替代错误处理。
- 副作用应集中在明确的位置，不要散落在纯计算代码中。

## 7. 功能备注强制规范

> 本节是硬性要求：**每个模块、类、函数、方法、测试、脚本入口都必须有功能备注。**
> 功能备注不能为空，不能只重复名称，不能使用自动生成的占位文本。

### 7.1 备注的用途

功能备注用于回答：

- 这段代码为什么存在；
- 它解决什么问题；
- 它如何被使用；
- 它依赖什么前提；
- 它会产生什么副作用；
- 它不负责什么。

功能备注不是给编译器看的，而是给未来的维护者、审查者和调用方看的。

### 7.2 模块级备注

每个源码文件必须有模块级 docstring，说明：

- 该模块负责什么；
- 所在层次或职责范围；
- 主要对外接口；
- 不负责什么；
- 如有必要，说明重要副作用或资源。

示例：

```python
"""订单应用服务。

负责订单创建、取消和状态迁移的用例编排。
不负责数据库实现、HTTP 参数解析或前端展示。
"""
```

### 7.3 类备注

每个类必须有类级 docstring，至少说明：

1. **职责**：这个类负责什么。
2. **角色**：入口、服务、领域模型、适配器、工具、配置等。
3. **生命周期**：由谁创建、持有多久、是否持有资源。
4. **边界**：明确不负责什么。
5. **对外能力**：主要公共方法和状态不变量。

示例：

```python
class OrderService:
    """订单用例编排服务。

    职责：协调订单模型、库存接口和订单仓储。
    生命周期：由应用容器创建，无长期外部资源。
    边界：不实现支付网关，不负责 HTTP 响应格式化。
    对外能力：create_order()、cancel_order()。
    """
```

### 7.4 函数与方法备注

每个函数和方法都必须有功能备注，包括私有函数和工具函数。

备注至少包含：

1. **目的**：为什么需要这个函数。
2. **输入**：关键参数的业务含义和前置条件。
3. **输出**：返回值、生成的数据或状态变化。
4. **副作用**：是否写文件、访问网络、修改状态、发消息。
5. **约束**：重要不变量、异常、性能限制或安全要求。

示例：

```python
def reserve_stock(order_id: str, items: list[OrderItem]) -> Reservation:
    """为订单预留库存。

    输入：已校验的订单 ID 和订单项列表。
    输出：库存预留记录；失败时抛出 InventoryUnavailable。
    副作用：调用库存服务并写入预留记录。
    约束：调用方必须保证同一订单不会并发重复预留。
    """
```

不合格示例：

```python
def reserve_stock(order_id, items):
    """预留库存。"""  # 无法说明输入、输出、失败方式和副作用
```

### 7.5 测试函数备注

每个测试函数必须有备注，说明：

- 验证的场景；
- 预期行为或不变量；
- 失败时代表什么问题。

示例：

```python
def test_reserve_stock_rejects_insufficient_inventory() -> None:
    """验证库存不足时返回可识别的业务错误且不创建预留记录。"""
```

### 7.6 特殊方法备注

以下方法必须额外说明生命周期或协议语义：

- `__init__`：构造职责、参数要求、初始化资源和对象不变量。
- `__enter__` / `__exit__`：资源获取和释放时机。
- `__aenter__` / `__aexit__`：异步资源生命周期。
- `__call__`：调用语义和副作用。
- `__iter__`：迭代顺序、终止条件和是否可重复迭代。
- `__len__` / `__getitem__`：集合语义、边界和复杂度（如适用）。

### 7.7 入口与脚本备注

CLI、HTTP handler、定时任务、消息消费者、脚本入口必须说明：

- 用户或系统如何触发；
- 输入来源；
- 输出和退出码；
- 错误处理方式；
- 是否需要幂等；
- 是否有权限或安全检查。

### 7.8 备注写作要求

- 使用完整句子，不使用“处理数据”“实现逻辑”等空泛描述。
- 优先描述业务语义，不重复类型签名。
- 在语言和风格上与项目保持一致。
- 修改行为时必须同步修改备注。
- 备注与代码冲突时，以修正备注或拆分代码为准，不能放任过期。
- 生成式注解或 LLM 生成的语义摘要可以放在独立侧车文件，但不能替代源码中的人工功能备注。

### 7.9 备注质量检查

提交前检查：

- [ ] 每个新增/修改的模块有模块 docstring。
- [ ] 每个新增/修改的类有职责、角色、生命周期和边界。
- [ ] 每个新增/修改的函数/方法有目的、输入、输出、副作用和约束。
- [ ] 每个新增/修改的测试有场景和预期不变量。
- [ ] 特殊方法已说明生命周期或协议语义。
- [ ] 备注没有空泛表述。
- [ ] 备注与当前实现一致。

## 8. 命名与代码风格

### 8.1 命名

- 名称应表达业务含义，不使用无意义缩写。
- 布尔值使用 `is_` / `has_` / `can_` 等可判断前缀。
- 集合使用复数或明确的集合语义名称。
- 工厂、仓储、适配器、服务等角色应在名称中体现。
- 避免 `Manager`、`Helper`、`Utils` 等过度泛化名称，除非职责确实通用。

### 8.2 类型

- 公共函数必须有参数和返回值类型。
- 复杂数据结构应使用 dataclass、TypedDict、Protocol 或明确的类型别名。
- 避免在公共接口中传递无结构的 `dict[str, Any]`。
- 类型标注不能代替功能备注。

### 8.3 函数长度与复杂度

- 单个函数只承担一个清晰职责。
- 复杂条件应提取为有业务名称的函数。
- 嵌套层级过深时优先拆分。
- 纯计算逻辑与 IO 逻辑应分离。

### 8.4 注释

- 注释解释“为什么”，不是重复“代码做了什么”。
- 临时绕行方案必须说明原因、范围和移除条件。
- 不允许提交无说明的 TODO、FIXME 或占位实现。

## 9. 错误处理与日志

- 可预期错误使用明确异常类型或错误结果。
- 捕获异常时必须有处理动作，禁止空 `except`。
- 不要用异常做普通控制流。
- 错误信息应包含足够上下文，但不泄露敏感信息。
- 日志级别应与事件严重性匹配。
- 日志中不得输出密钥、令牌、密码或完整个人敏感信息。
- 对外错误信息与内部诊断信息应区分。

## 10. 安全与依赖

- 所有外部输入都视为不可信。
- 执行命令、访问文件、查询数据库和发起网络请求时必须限制作用域。
- 不硬编码密钥、令牌或生产凭据。
- 新增第三方依赖前必须确认：
  - 是否真的需要；
  - 是否有维护；
  - 许可证是否兼容；
  - 是否引入不必要的运行时或供应链风险。
- 优先使用标准库和已有依赖。
- 依赖版本应可复现。

## 11. 标准开发流程

### 11.1 修改前

1. 阅读项目 README、架构文档和当前约定。
2. 确认改动属于哪一层。
3. 确认公共接口和数据契约。
4. 确认状态、副作用和错误处理。
5. 确认测试方式和文档影响。

### 11.2 实现顺序

推荐顺序：

```text
数据模型与契约
  → 核心逻辑
  → 外部适配
  → 入口/接口
  → 校验与错误处理
  → 测试
  → 文档
```

不要先写展示层，再从展示层反推业务逻辑。

### 11.3 修改后

至少执行项目定义的：

```bash
<format-command>
<type-check-command>
<unit-test-command>
<integration-test-command>
<build-command>
```

如果项目没有定义命令，提交前必须说明实际执行的验证方式。

## 12. 测试约定

### 12.1 测试层级

- 单元测试：纯函数、模型、规则和边界条件。
- 集成测试：模块协作、数据库、文件、网络适配器。
- 端到端测试：关键用户路径。
- 回归测试：已修复缺陷和非预期行为变化。

### 12.2 测试要求

- 测试必须可重复、可独立运行。
- 测试不应依赖执行顺序。
- 测试数据应显式构造或使用 fixture。
- 涉及时间、随机数、网络和文件系统的测试必须可控。
- 公共 API 必须有成功、失败和边界测试。
- 缺陷修复必须先有可复现测试。
- 测试不能只验证“没有抛异常”，要验证行为结果。

### 12.3 测试备注

测试函数必须写功能备注，说明场景和预期不变量。

## 13. 文档约定

- 根 README 是项目总入口。
- 架构、接口、数据契约和部署说明应各有明确文档。
- 当前有效文档与历史归档应分开。
- 文档中的命令必须可执行。
- 文档中的链接必须可解析。
- 数据格式或公共接口变化时，文档和测试同步更新。
- 过程性交接文档在阶段完成后归档，不应长期混在当前权威文档中。

## 14. 禁止事项

以下行为应视为破坏项目长期可维护性：

1. 同一业务规则重复实现。
2. 展示层重新推导业务事实。
3. 公共接口没有类型或功能备注。
4. 修改行为但不更新测试和文档。
5. 捕获异常后静默忽略。
6. 在构造函数中执行不可撤销的外部副作用。
7. 在公共接口中传递无结构大字典。
8. 使用全局可变状态隐藏依赖。
9. 引入不必要的第三方依赖。
10. 提交空泛 TODO、占位实现或未说明的临时绕行。
11. 测试依赖执行顺序或外部不稳定环境。
12. 日志输出敏感信息。
13. 为了短期方便绕过架构边界。
14. 新增/修改模块、类、函数或测试却不写功能备注。

## 15. 提交前检查清单

### 架构

- [ ] 代码放在正确的层次和模块。
- [ ] 依赖方向没有倒置或循环。
- [ ] 公共接口与内部实现已分离。
- [ ] 没有隐藏的全局状态或隐式副作用。

### 契约

- [ ] 输入、输出、异常和副作用已明确。
- [ ] 数据结构有类型和字段说明。
- [ ] 数据或接口变化已处理兼容性。
- [ ] 外部输入已在边界校验。

### 功能备注

- [ ] 模块 docstring 已写。
- [ ] 类 docstring 已写。
- [ ] 函数/方法 docstring 已写。
- [ ] 测试函数 docstring 已写。
- [ ] 特殊方法说明生命周期或协议语义。
- [ ] 备注没有空泛表述，且与实现一致。

### 质量

- [ ] 错误处理完整。
- [ ] 日志不泄露敏感信息。
- [ ] 资源有释放路径。
- [ ] 没有不必要的依赖。
- [ ] 测试覆盖成功、失败和边界情况。
- [ ] 格式化、类型检查、测试和构建通过。

### 文档

- [ ] README 或相关文档已更新。
- [ ] 命令和链接可执行/可解析。
- [ ] 历史文档已归档。
- [ ] 版本号和变更说明已同步。

## 16. Definition of Done

一个改动只有同时满足以下条件才算完成：

1. 代码符合项目分层和依赖方向。
2. 公共接口、数据结构、错误和副作用都有明确契约。
3. 每个新增/修改的模块、类、函数、方法和测试都有高质量功能备注。
4. 关键路径和边界条件有可重复测试。
5. 格式化、类型检查、测试和构建通过。
6. 文档、命令、链接和版本信息已同步。
7. 没有引入隐藏状态、重复事实、无说明依赖或未处理的安全风险。
8. 审查者仅通过代码、功能备注和文档就能理解改动意图与边界。

本 Skill 是通用基线；项目可以在自己的约定文档中增加更严格的领域规则，但不得降低本 Skill 对功能备注、显式契约和可验证性的要求。
